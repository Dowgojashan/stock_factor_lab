## Part 1：FCV策略產生（Phase 1 → Phase 4）

### 1.0 定位：這一段在做什麼

FCV框架：`F（體質因子）× C（動態條件）× V（估值濾網）`。Phase 1-4是老師訂的SOP，
一次只開一個維度，逐步疊加，每一階段都先跑回測、再分析結果、決定哪些組合可以晉級到下一階段：

```
Phase 1  單因子健檢（9桶線性/單調性檢定）           → 決定哪些因子「單獨看」有效
Phase 2  F1×F2不對稱配對（primary嚴格、secondary寬鬆）→ 決定哪些「因子組合」有效
Phase 3  加動態條件C（20種）                        → 決定「加時機判斷」有沒有用
Phase 4  加估值濾網V（PE相對估值）                   → 決定「加便宜度篩選」有沒有用
```

每個Phase都是「先跑回測（`phaseN_*.py`裡沒有`_analyze`的那支）→ 再分析結果
（`phaseN_analyze.py`）」兩支程式一組，**必須依序執行**，後面的Phase會直接讀前面
Phase分析完的結果檔案當輸入。

⚠️ **執行前提**：所有指令都要在 `code/` 目錄下執行（`cd code`），因為`config.ini`
是相對路徑讀取；且需要資料庫連線正常（`database.py`透過`pymysql`連MySQL/MariaDB）。

### 1.1 前置：原始資料層（不是你會主動執行的腳本，是背景引擎）

以下四支在**根目錄**（不在`code/`裡），是Phase 1-4執行時在背景被呼叫的資料存取層，
**不是獨立跑的流程步驟**，這裡列出來只是讓你知道資料從哪裡來：

| 檔案 | 角色 | 讀什麼 | 產出什麼 |
|---|---|---|---|
| `database.py` | `Database(market)`類別，開DB連線＋市場過濾SQL | MySQL `company`/`stock`/`factor`/`factorvalue`/`taiex`/`sp500`/`russell3000`表 | 回傳DataFrame，不寫檔 |
| `get_data.py` | `Data(market)`類別，初始化時就把股價/財報/基準資料抓下來 | `Database`物件 | 記憶體內的資料，不寫檔 |
| `format_data.py` | 純函式：把長格式資料轉成寬格式（`format_price_data`／`format_report_data`），US用`filing_date`避免前視偏誤、TW用財報期別+法定公告期限校正 | `get_data.py`抓來的DataFrame | 轉換後的寬格式DataFrame，不寫檔 |
| `combinations.py` | `sim_conditions()`跑`backtest.sim()`，是實際跑回測的引擎 | 條件遮罩＋`backtest.sim` | 記憶體內的`Report`物件 |

→ 背景呼叫`database.Database(market)`查DB → `format_data`轉換 → 快取在記憶體。
**這一層你不用手動跑，Phase 1-4的每支程式一開始建立`MarketData`物件時就會自動觸發。**

### 1.2 Phase 1：單因子健檢

**跑回測：**
```bash

python phase1_linearity.py --market TW                    # 全部20個因子，預設批次

  （`stats.parquet` + 逐策略子資料夾 + `_DONE`標記）

python phase1_analyze.py --market TW --bench universe
```

  - **`_analysis_outputs_phase1/{market}_phase1_linearity.csv`**——這是Phase 2的輸入，
    每個因子有Spearman ρ、形狀分類、判定結果（✅過關／⚠️邊際／⚠️只取極端桶／❌淘汰／🚫前瞻偏誤）
  - `_analysis_outputs_phase1/{market}_phase1_curves.png`（9桶曲線圖）
- **該看什麼**：CSV裡的`判定`欄——這決定了每個因子在Phase 2能不能當primary

（選用的穩健性檢定，非必跑：`phase1_cleanperiod_check.py --market TW`、

### 1.3 Phase 2：F1×F2不對稱配對

**跑回測：**
```bash
python phase2_pairing.py --market TW --variant openSec
```
- 輸入：`phase_variants.get("openSec", "TW")`——依Phase 1的CSV把因子分成primary/secondary
  兩組（見1.5變體說明），3桶（不是9桶）
- 輸出：`code/results_artifacts/{market}_L2_openSec_M/`
- ⚠️ 執行前會呼叫`phase_variants.assert_pool_unchanged()`——**如果因子池變了（例如加了新因子）
  但舊的同名輸出資料夾還在，會直接報錯擋下**，避免靜默沿用舊資料。加新因子時記得先把舊資料夾

**分析結果：**
```bash
python phase2_analyze.py --market TW --variant openSec --bench universe
```
- 輸入：讀`stats.parquet`
- 門檻：primary要贏基準≥2pp（`primary_margin=0.02`）、secondary輸基準不能超過1pp

- 輸出：
  - **`_analysis_outputs_phase2/{market}_L2_openSec_體質檢查表.csv`**——這是Phase 3的輸入，

### 1.4 Phase 3：加動態條件C

**跑回測：**
```bash
python phase3_conditions.py --market TW --variant openSec
```
- 輸入：Phase 2的`體質檢查表.csv`（`晉升`=True的F組合）＋20種C（見下方定義）
- **只對F白名單裡的組合**展開C，不是全部組合都加C重跑
- 輸出：`code/results_artifacts/{market}_L3_openSec_M/` + `_MANIFEST.json`（記錄用的是哪個白名單版本）
- 若Phase 2的分析還沒跑過，這支會直接`FileNotFoundError`擋下

**C的定義**（`sweep_config.py`）：固定用`ROE`/`EPS`/`FCF_P`三個因子 × 7種條件類型
（較上季升、較兩季前升、近4季最高、近8季最高、YoY成長、YTD均值贏去年同期均值、
YTD均值贏去年全年均值），扣掉1個不合理組合，共 **3×7−1 = 20種C**。

**分析結果：**
```bash
python phase3_analyze.py --market TW --variant openSec --bench universe
```
- 邏輯：每個F組合自己的「C=None」當基準，C的貢獻＝CAGR(F+C)−CAGR(F,None)，
  **不同F組合的C增益不能直接混在一起比較**（有控制F這件事）
- 輸出：
  - `_analysis_outputs_phase3/{market}_L3_openSec_C_ranking.csv`（C增益排名）
  - `_analysis_outputs_phase3/{market}_L3_openSec_candidate_strategies.csv`（Phase 3階段的候選清單，
    **注意這還不是最終候選池，會被Phase 4取代**）
  - `_analysis_outputs_phase3/{market}_L3_openSec_C_gain.png`

🔑 **補充分析手法（2026-09-29對照過去報告補上）**：`C_ranking.csv`除了看單一C排名，
過去報告會**把20個C依來源因子分組**（ROE衍生7個／EPS衍生7個／FCF_P衍生6個，
用C的名稱前綴對應`sweep_config.py`裡的來源因子即可分組），看「哪個來源因子衍生出來的
動態條件整體比較有貢獻」——這比看單一C的排名更能看出穩定的規律，也是判斷「新加的
成長因子要不要也衍生自己的C」的依據之一。這不是另一支程式，是對`C_ranking.csv`
做的人工分組讀法，沒有額外指令。

### 1.5 Phase 4：加估值濾網V

**跑回測：**
```bash
python phase4_valuation.py --market TW --variant openSec
```
- **只補跑v1**（`V_MODES=("v1",)`）——v0直接沿用Phase 3的結果，因為Phase 3本來就是
  在v0（無估值濾網）條件下跑的，同一組F×C不用重跑
- V的定義：PE低於自己過去4季均值、但高於過去4季最低值（「相對自己歷史便宜，但不是最低點」）
- 輸出：`code/results_artifacts/{market}_L4_openSec_M/` + `_MANIFEST.json`

**分析結果（產生最終候選池）：**
```bash
python phase4_analyze.py --market TW --variant openSec --bench universe
```
- 輸入：Phase 3的`L3`（v0）+ Phase 4的`L4`（v1），都先用Phase 2的體質檢查表過濾一次，
  用`F+C`配對比較ΔCAGR/ΔMDD
- 輸出：
  - `_analysis_outputs_phase4/{market}_L4_openSec_v0v1_pairs.csv`
  - **`_analysis_outputs_phase4/{market}_L4_openSec_final_candidates.csv`**
    ——🔴**這就是整個Phase 1-4流程的最終產物**，v0+v1聯集、篩選條件是
    「平均持股數≥10 且 CAGR贏基準」。**研究部stage0只讀這個檔案。**
  - `_analysis_outputs_phase4/{market}_L4_openSec_V_effect.png`

🔑 **補充分析手法（2026-09-29對照過去報告補上）**：`v0v1_pairs.csv`過去報告的標準讀法
是畫成**四象限圖**——橫軸ΔCAGR（加V後報酬變化）、縱軸ΔMDD（加V後風險變化，負值＝
回撤變深），四象限＝①報酬升風險降（雙贏）②報酬升風險升（換取報酬）③報酬降風險降
（換取穩定）④報酬降風險升（雙輸）。用這四象限分布，加上同時看「持股數變化」（加V後
通常會讓持股集中，波動可能因此放大），才能完整判斷V濾網對這批F×C組合是不是有效，
不是只看`final_candidates.csv`最後選了幾檔。這也不是額外指令，是對`v0v1_pairs.csv`
的標準讀法。

### 1.6 四個變體：strict／openSec／relaxed／all

定義在`code/phase_variants.py`，差別在Phase 1結果怎麼分配到primary/secondary：

| 變體 | primary | secondary |
|---|---|---|
| strict | 只有✅過關 | ⚠️邊際＋⚠️只取極端桶 |
| relaxed | ✅過關＋⚠️邊際＋⚠️只取極端桶 | 同上 |
| all | 全部可用因子 | 同上（等於沒篩選，當控制組）|
| **openSec（採用）**| 只有✅過關 | **全部可用因子**（不篩）|

**採用openSec的理由**：Phase 1測的是「因子自己能不能單調預測」，但secondary的功能是
「提供不同構面資訊」，兩件事不一樣；實測過度限制secondary會把全池表現最好的策略篩掉。
`VARIANT="openSec"`寫死在`code/research/paths.py:37`。

🔑 **這個決定是怎麼驗證出來的（2026-09-29對照過去報告補上，方法本身，不列具體數字）**：
四個變體全部各自跑一次Phase 2-4，比較各自最終候選池的整體CAGR中位數／p90——
如果新增因子後想確認因子池開放程度的設計還適不適用，可以照這個方法重新驗證一次：
**放寬primary會拉低整池中位數**（代表Phase 1的線性檢定確實有效過濾掉不該當主力的因子）；
**過度限制secondary則會誤殺**（被Phase 1淘汰的因子當secondary時仍可能有貢獻，全部
關閉secondary會讓最終候選池少掉一大塊有效組合）。這兩個方向同時成立，才是openSec
被採用的完整理由，不是只看單一方向。

### 1.8 🔑 實際加入新因子（例如新的成長型因子）的完整步驟

這是接下來要做的事，這裡先把驗證過的正確程序記錄清楚：

1. **確認資料庫已有這個因子的值**（`factor`/`factorvalue`表，`factor_name`小寫）——
   Phase 1-4本身不負責收集/計算因子原始資料，只負責回測已存在的欄位。沒有的話要先讓
   collector補（這步不在這份文件範圍內）。
2. 把因子名稱加進`code/phase1_linearity.py`的`FACTORS`清單。
3. ⚠️ **同時檢查**`code/fcv_core.py`裡的`FACTOR_FIELDS`常數——這個清單目前**沒有跟
   `FACTORS`完全對齊**（缺`MOM1`/`ACCRUAL`/`REV_G`/`VOL`/`NETDEBT_EBITDA`等幾個），
   要判斷新因子要不要同時加進這裡（會影響可交易宇宙的認定範圍，不只是因子池），
   **這點目前沒有定論，動手前要先確認**。
4. **封存舊的Phase 2-4輸出資料夾**（`code/results_artifacts/{market}_L2*/`、`L3*/`、`L4*/`
   等同名資料夾）——不封存的話，`phase_variants.assert_pool_unchanged()`會偵測到因子池
   變了但標籤沒變而直接報錯擋下。
5. 依序重跑：`phase1_linearity.py`→`phase1_analyze.py`→`phase2_pairing.py`→
   `phase2_analyze.py`→`phase3_conditions.py`→`phase3_analyze.py`→`phase4_valuation.py`→
   `phase4_analyze.py`，每支都帶`--variant openSec`（其他變體要不要一起重跑，看是否需要
   跟舊結果對照）。TW/US兩個市場都要各跑一輪。
6. **重跑`stage0_index.py`（研究部，見Part 2）之前**，要先更新`code/research/contracts.py`
   裡的硬編碼斷言常數：`EXPECTED_ROWS`（目前TW 7128/US 8682，驗證過現在frozen parquet
   實際列數是15,810＝7,128+8,682，跟這個常數一致）、`EXPECTED_F2_EMPTY`、`EXPECTED_F_COMBOS`、
   `FACTOR_TYPE_MAP`（新因子要歸類到哪個因子類別，沒歸類`stage0_index.py`會直接
   `ValueError`擋下）。這些是嚴格斷言，數字對不上會直接讓整個stage0失敗，不是警告。

### 1.9 另一條容易混淆的路：候選因子探索批次（`run_factor_batches.py`）

🔴 **這條路徑不是Phase 1-4 SOP的一部分，是一個獨立的診斷工具**，用途是「這個候選因子
值不值得正式收進因子池」的探索性測試，**跑出來的結果不會進入正式候選池**（研究部stage0
完全不讀它的輸出）。

```bash
python run_factor_batches.py --market TW --candidates MY_NEW_FACTOR
python analyze_batch.py --label TW_batch_MY_NEW_FACTOR_M
```
- 邏輯：把候選因子跟固定的ROE/EPS/FCF_P放一起、用N=5桶跑一次簡化版回測
- 輸出：`code/results_artifacts/{market}_batch_{candidate}_M/` + `_analysis_outputs/{label}/`
  （20張圖，對應論文第四章圖鑑格式）

### 2.8 背景機制：`freeze.py`（凍結／DD-08）為什麼重跑是安全的

不是你會主動執行的腳本，是每個stageN程式內部都會呼叫的函式庫：
- 每個階段跑完，呼叫`freeze.write_manifest()`把這階段的輸入雜湊、輸出雜湊、參數、
  git commit SHA全部寫進該階段輸出目錄下的`MANIFEST.json`
- 下一個階段開始執行時，呼叫`freeze.verify_inputs()`重新對一次雜湊，
  **只要上游檔案被誰動過（不管是不小心改到還是重跑用了不同資料），雜湊對不上就直接
  丟`FreezeViolation`擋下**，不會讓你在不知情的情況下用到過期/不一致的上游資料
- 這就是為什麼「重跑某一階段安全」——下游只要接著重跑，會自動偵測到上游變了

真正的核心是28支無底線的模組，分兩層：

- **Layer 1（五層應用架構，2026-09-08~14建的）**：`config.py`／`engine.py`／`risk.py`／

**查證後確認一件很關鍵的事：這兩層目前是斷開的，不是一條串好的pipeline。**

- `clustering.py`（Layer 1，代表策略挑選）的結果**只存在記憶體裡，不會寫成檔案**
- `simulate.py`（Layer 2，實際跑季度監控迴圈）的候選池是**寫死在程式碼裡的一組固定
  參數**（`simulate.py:316-321`：`tree_key="TW", scheme="E", window_no=4,
  k_mode="silhouette_is", ratio="legacy", allocation=..., group="A_hrp"`），
  直接查`walkforward_members.parquet`裡對應這組參數的那一列策略清單，
  **完全沒有呼叫`clustering.py`**
- **結論**：現在要讓Layer 2監控系統跑在一個新的候選池上（例如Part 2用新成長因子重跑出來
  的HRP樹/走勢矩陣），**沒有設定檔選項或指令參數可以做到這件事**，必須手動改
  `simulate.py:316-321`這段程式碼的寫死參數，指向新的候選池所在的窗次/scheme組合。
  這不是文件沒寫清楚，是程式碼架構現況真的是這樣，先誠實記在這裡，避免之後卡在這裡
  找不到原因。

另外查證時**額外抓到一個獨立的架構不一致**：`_run_exclude_v1_formal.py`／
`_run_rolling_w6_formal.py`這兩支並不是呼叫`simulate.py`的`run_simulation()`，
而是呼叫另一支診斷腳本`_check_rolling_production_simulation.py`裡自己定義的
`run_rolling_simulation()`——**實質上有兩套平行、不完全一致的季度模擬迴圈實作**，
不是只有`simulate.py`一套。這是既有的技術債，這裡先如實記錄，不是這次要處理的事。

🔑 **這個斷層可以用系統原本的「快慢時鐘」設計來理解，但不完全是設計本身造成的**
（2026-09-29對照9/15簡報補上）：

- **快時鐘（季度）**：每季重新用最新財報跑一次選股條件，決定現在實際要買哪些股票，
  對應「投組再平衡」——`simulate.py`每季呼叫`resolve_strategy_holdings.resolve_holdings()`
  做的就是這件事，**這部分正常運作，不受上面的斷層影響**
- **慢時鐘（2年）**：重新做HRP分群、重新挑代表策略，對應「策略檢視／代表策略汰換」——
  理論上是`clustering.py`該負責的部分
- 快時鐘每季自動觸發沒問題；但**慢時鐘連「手動觸發、換一批新代表策略」的參數化管道
  都沒有**——不是「兩年才觸發一次是正常的，現在還沒到時間」，是「就算真的要觸發，
  也沒有做好的方式可以做」，這才是上面斷層的真正意涵。你已經確認這次實驗範圍只做
  快時鐘、慢時鐘維持只有設計不用補，這裡純粹記錄清楚，不是待辦。

#### 3.2.1 Hot Segment／Coverage Tilt的設計（跟M1-D／W2c同一套架構，平行運作）

Hot Segment在預測層（3b）跟M1-D平行、各自獨立判定；Coverage Tilt在動作空間跟W2c平行、
各自獨立的觸發條件。兩組機制**互不依賴**——M1-D管的是「大盤有沒有變得比登記時更集中」，
Hot Segment管的是「我們的持股有沒有跟上市場正在噴的股票」，是不同的風險面向，所以分開判定、
分開觸發，不是其中一個包含另一個。

🔑 **對照`實戰監控Agent系統_設計文件.md`§7.4b（Hot Segment完整規格）重新確認過，
這裡有兩層粒度不同的「覆蓋率」，不能混用同一個計算——之前的草稿把兩者寫成同一件事，
這裡修正**：

**Hot Segment判定（市場層級聚合，用於觸發）**：
- 每季末，用過去N個月報酬排序全市場，取報酬最高的前X%股票當熱門股清單（`HotSegment(t)`）——
  對應業界動能因子的標準定義（Jegadeesh and Titman 1993）。N/X已校準：TW取3個月、
  US取6個月、XM統一10%（校準過程沿用`_design_test_hot_segment.py`，正式接線時把
  `monthly_close()`／`hot_segment()`這兩個函式搬進`monitor.py`）
- **市場層級覆蓋率**`coverage_count`＝這批熱門股裡，有被「至少一個代表策略」選中的比例
  （用`selects_symbol()`逐檔判斷，不是抽樣估計），算兩種版本：**檔數版coverage_count**
  （主要判準）、**市值加權版coverage_mktcap**（已驗證波動遠大於檔數版、自相關弱，
  只能當輔助參考，**不能拿來觸發**）
- 門檻用歷史資料算p25（觀察線）／p10（異常線）分位數，低於p10才判定TRIGGERED——
  注意判斷方向跟M1-D相反（M1-D是「偏離越高越異常」，Hot Segment是「覆蓋率越低越異常」）
- 狀態機跟M1-D同樣是NONE/OBSERVING/TRIGGERED三態，`triggers.evaluate_hot_segment_quarter()`
- M1-D跟Hot Segment**完全獨立觸發**，不是誰包含誰——可能同時觸發、只有一個觸發、
  或都不觸發，四種狀態都要各自呈現，不能互相掩蓋

**Coverage Tilt動作（策略層級，用於權重調整，粒度跟上面不同）**：
- 觸發條件：跟W2c的邏輯對稱——上一季Hot Segment狀態為TRIGGERED，且上一季agent決定
  選了這個動作，兩者同時成立，下一季才套用（比照W2c的「核准有一季時間差」）
- 套用時機：`resolve_portfolio_weights()`裡呼叫`weights.apply_coverage_tilt()`，
  底層公式用的是**每個代表策略自己的**覆蓋比例（不是上面市場層級的`coverage_count`）：
  `coverage_frac(r,t) = |holdings(r,t) ∩ HotSegment(t)| / |HotSegment(t)|`，
  `w_r(t) ∝ (1/R) × (1 + β·coverage_frac(r,t))`，β=0時退回純等權，只調策略間的相對權重，
  策略內部持股不動（正式接線時要新增一支算逐策略`coverage_frac`的函式，跟市場層級的
  `coverage_count`是兩支不同函式，不要共用；權重公式函式建議命名
  `coverage_tilt_weights(holdings, covers, uids, beta)`，`weights.py`裡已經有一個同名的
  `tilt_weights(w0, mcap_row, alpha)`是W2c自己的市值傾斜公式，兩者完全不同，不能撞名）
- β值：正式接線用**β=5**（已測試網格{0,1,2,5,10}的中段值），刻意保守
- 跟W2c一樣，這是**每季重新評估、不是一次開了就一直開**——Hot Segment狀態回到非
  TRIGGERED，Coverage Tilt自動停用

#### 3.2.2 🔑 2026-10-01：用 Active Share 量化「等權/W2c跟大盤差多少」（新分析，非正式接線功能）

背景：台股加成長因子重跑後，發現2024-2025這兩年策略池（不管哪個版本）都大幅落後TAIEX
（即使套用W2c強制市值傾斜，8季仍落後約37pp）。查證過程中釐清兩件事：
① 台積電一檔股票貢獻了TAIEX同期總報酬的約72%（股價漲161.6%、平均市值權重31.5%）；
② 我們的策略池對「熱門股」（近3個月動能前10%）的聯集覆蓋率跟對「全市場」的聯集覆蓋率
其實差不多（甚至熱門股覆蓋略高於全市場覆蓋，39.2% vs 29.2%），所以「選不到熱門股」
不是問題核心。真正能把這兩件事串起來、且有真實業界文獻支持的角度，是 **Active Share**
（Cremers & Petajisto, 2009）。

**定義**：
```
Active Share = (1/2) × Σ|w_fund,i − w_benchmark,i|　（對每一檔股票加總，i 跑遍基金+benchmark的聯集）
```
0%＝持股跟benchmark完全一樣（純被動複製）；100%＝跟benchmark完全沒有重疊的股票。
這不是本專案自創指標，是真實業界會用（但非強制揭露）的概念；業界常見分級：
<20%「偽主動」(closet indexing)、20-60%中度主動、>60%「真正主動」；美股實測中位數：
大型股基金約61%、小型股基金約93%（來源見下方Sources，2026-10-01查證）。

**算法**（`w_benchmark`用`report:mktcap`算出的真實市值權重近似TAIEX；`w_fund`用
`resolve_portfolio_weights()`算出的投組權重；⚠️ 比對時務必用`pd.isna()`處理NaN市值，
不能用`dict.get(key, 0.0) or 0.0`這種寫法——key存在但值是NaN時，`NaN or 0.0`還是NaN，
這次算的時候就踩到一次，等權版一度全部算成NaN）：
```python
def active_share(w_fund: dict, w_bench: pd.Series) -> float:
    all_syms = set(w_fund) | set(w_bench.dropna().index)
    diff = sum(abs(safe_get(w_fund, s) - safe_get(w_bench.to_dict(), s)) for s in all_syms)
    return diff / 2.0
```

**實測結果**（TW scheme E window4 A_hrp legacy equal，35檔，2024Q1~2025Q4）：

| 版本 | Active Share（8季平均） | 範圍 |
|---|---|---|
| 等權（control0） | **87.7%** | 85.8%~90.1% |
| W2c傾斜後 | **71.3%** | 66.3%~78.7% |

**解讀**：等權版Active Share接近業界小型股主動基金中位數（93%），代表這是個「幾乎完全
不跟隨大盤權重」的投組，風格上極端主動；W2c傾斜後往大盤方向靠攏但仍遠高於「偽主動」
門檻，落在業界大型股主動基金中位數（61%）附近。**這給了「落後大盤37pp」一個比「選不到
大型股」更站得住腳的解釋**：Active Share越高，報酬跟benchmark的落差本來就可能越大（不管
正負），這兩年剛好落在輸的那一側是因為benchmark報酬被單一個股極端集中貢獻，不是策略
選股邏輯本身的缺陷——換一個市場狀態（分散式全面上漲），同樣高的Active Share可能會讓
投組大幅贏過大盤。寫論文時這個角度比單純講市值集中度更有文獻依據，建議採用。
