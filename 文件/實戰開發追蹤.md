#### ✅ X 值凍結（2026-09-17）

### A2／A3 完成紀錄（2026-09-16）：對照 0 真實已實現績效基準線

|---|---|---|

方向與 §1.1 一致（加權效果主導），數值不同是因為這次用**同一套系統**三個數字

### 🔴🔴 D2 洩漏掃描在本系統的識別碼命名下有真實盲區，已深入修正（2026-09-17）

**發現**：做 3a（回顧診斷）第一次真實呼叫時，D2 誤攔了完全正確的一句話

**追查後發現範圍更大、方向更危險**：欄位名稱本身（`q1_weight`、
`m1d_state_csv`）內含的雜散數字，會被 D2 當成「prompt 裡已提供的合法數字」，
如果 LLM 捏造一個剛好等於這些雜散數字的假數字（例如「1」），D2 完全抓不到
——這比「正確答案被誤攔」更嚴重，是「該擋的沒擋住」。用乾淨測試直接證實：

```

LLM輸出：「亂編的假數字約為一（1）成」
scan_for_leakage() → []（完全沒抓到，因為 q1_weight 的 1 洗白了它）
```

`memo.scan_for_leakage`／`_NUMBER_RE`（explain.py／memo.py 共用、已測試過的

數字」的識別碼（M0~M7、A0~A5、W1~W4、F1/F2、L1~L3、C2/C5、T8、
`q1_weight`、`m1d_state_csv`……），比對前一律把數字部分拿掉，只留字母骨架。

🔴 **修正過程中自己又踩到一個真 bug**：第一版正則（數字長度不設限）會把
JSON 跳脫換行符（字面上的 `\n`，反斜線加字母 n）緊貼日期數字時（例如
`...weight\n2024-09-30...`）誤判成「字母 n 開頭、含數字 2024 的識別碼」，
