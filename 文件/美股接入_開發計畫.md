## 0. 目標與範圍

把 FCV 因子回測系統擴充成**同一套系統 + market 參數**，同時支援台股與美股，作為後續 Agent 化與跨市場研究的資料/工具基礎。

- ✅ **納入範圍**：美股行情、財報、因子資料的抓取與入庫；讀取層（database/format_data/get_data）支援 market；回測費率/大盤基準分流；美股前瞻防護。
- ❌ **不在此文件範圍**：Agent 化（第三層）、Fund House 組合調度（第四層）、A3 配方產生器（另案，但與本案強耦合，見 §8）。

**核心原則**：所有台美差異**收斂在資料層**，`get()` 以上（`condition_factory`、`combinations`、`report_analysis`）完全共用。

## 1. 架構決策（已定）

**接法 A：FMP → 寫進 MySQL（沿用現有表）→ FCV 照常從 MySQL 讀。**

```
FMP API ──(美股 Collector：格式轉換/單位對齊/filing_date)──▶ MySQL `lab`
                                                                  │
                                                    database.py（依 market 查詢）
                                                                  │
                                                    format_data.py（前瞻防護分流）
                                                                  │
                                                    get_data.py  get(market=...)
                                                                  │
                                        ▼ 以上完全共用（不因市場改動） ▼
                            condition_factory / combinations / report_analysis
```

**為何用 A（而非在 get() 直接打 FMP）**：Fund House 要做跨市場組合，需輸出格式一致；批次回測需離線、可重現；資料庫成為台美的統一交會點。

## 2. 系統資料契約（美股最終要塞成的格式）

無論來源如何，最後都要變成這三種 `data.get()` 輸出：

| 呼叫 | 輸出 | 來源 DB 表 |
|------|------|-----------|
| `get("price:close")` 等 | index=日期、columns=股票代號 寬表 | `company` ⋈ `stock` |
| `get("report:ROE")` 等 | 同上寬表，值=因子值 | `factor` ⋈ `factorvalue` ⋈ `company` |
| `get("taiex:close")` | 大盤基準（美股需換 S&P500） | `taiex` 表 |

`factorvalue` 的長格式契約：`date / company_symbol / factor_name / factor_value`（＋本案新增 `filing_date`）。

## 3. FMP → 系統因子 對應表（含單位陷阱）

| 系統因子 | JSON 門檻 | FMP 端點 / 欄位 | FMP 單位 | 換算 |
|----------|----------|----------------|----------|------|
| ROE | 5/10/15/20（百分比） | `ratios` → `returnOnEquity` | 比例 0.15 | **×100** |
| DEBTRATIO | 0.35/0.55（比例） | `ratios` → `debtRatio` | 比例 | 免換 |
| FCF_P | 0/0.05（比例） | `key-metrics` → `freeCashFlowYield` | 比例 | 大致一致 |
| PE | — | `ratios` → `priceEarningsRatio` | 倍數 | 免換 |
| REVENUE | 動態(YoY) | `income-statement` → `revenue` | 絕對(USD) | 只做 YoY，可容忍 |
| EPS | 0/2（絕對值） | `income-statement` → `epsdiluted` | 絕對(USD) | ⚠️ **不可換算**（見 §8） |

## 4. 技術難點與解法

| # | 難點 | 現況/風險 | 解法 | 對應程式 |
|---|------|-----------|------|----------|
| 1 | **前瞻防護 / 公告日**（紅線） | `adjust_index_of_report` 用台股會計月份推公告日；美股會計年度不一（如 Apple 9 月底），會把年報誤判成 Q3。DB 美股 `date` 是期末日、無 filing date | 入庫記 FMP `fillingDate`（兩個 l），`factorvalue` 加 `filing_date` 欄；讀取時美股用 filing_date 當索引、跳過月份規則 | `format_data.py`、`database.py` |

| 3 | **代號語意** | 台股數字(2330) vs 美股英文(AAPL)；舊查詢有 `company_symbol>8700` 數值比較 | 代號一律當字串處理，全面檢查數值比較路徑 | `database.py`、`get_data.py` |
| 4 | **費率/稅 + 大盤基準** | `sim()` 寫死 `tax_ratio=3/1000`（證交稅）、`fee_ratio=1.425/1000`；`get("taiex")` 是台股加權 | 美股 `tax_ratio=0` + 美股手續費；基準換 S&P500 | `backtest.py`、`get_data.py`、`report.py`(待查) |

## 8. 與 A3（配方產生器）的耦合（重要）

**EPS 這類絕對值因子跨幣別不可比**（NT$2 ≠ US$2），無法靠單位換算沿用同一份固定門檻 JSON。
→ 這逼使 A3 對跨市場採用**分位數門檻**而非固定門檻。
→ 因此「美股銜接」與「A3 配方產生器」應**一起規劃**：共用一套產生邏輯，各市場產出各自的 JSON。

## 9. FMP 實務注意事項

- `fillingDate`（兩個 l）+ `acceptedDate`，別用一般拼法 `filingDate`。
- 財報端點帶 `period=quarter`，別混到 annual。
- 決定用 `adjClose`（還原價）或原始價，並與台股口徑一致。
- 歷史市值用 `historical-market-capitalization`（`profile` 只有即時）。
- 倖存者偏誤：用 `delisted-companies` 補下市公司。
- API 額度/速率：~9400 檔 × 多報表 × 多季，抓取要分批、快取、可續傳。

## 12. D3 分析：US Collector 該放哪

**選項**
- **A｜同 repo**：US collector 放進 `stock_factor_lab`。
- **B｜獨立 US collector repo**：自成一包，鏡像台股的 `TW_stock_factor_collector`。
- **C｜統一 collector repo**：自己擁有一包，同時含 TW（改寫）+ US collector，與 `stock_factor_lab` 分開。

**四個面向分析**
| 面向 | 同 repo (A) | 分開 (B/C) |
|------|------------|------------|
| 沿用現有架構 | ✗ 與台股「collector 獨立」慣例相悖 | ✓ 台股本來就分開，對稱一致 |
| 乾淨程度 | ✗ 把 API key、HTTP/ETL 依賴、原始 JSON 混進「純讀取/回測」repo | ✓ FCV repo 維持乾淨的 DB 消費者 |
| 開發難易度 | ✓ 起步略快（共用 config/DB code） | ~ 多一次 repo 建置；DB 連線樣板約 30 行、重寫成本低 |
| 分開的麻煩 | — | ~ 兩包要維護；schema 變更需跨 repo 協調（但 schema 本就是唯一契約、變動少） |

**關鍵判斷**：collector 與 FCV 的**程式耦合極低**——它們只透過「DB schema」這個契約溝通，資料單向流動（collector 寫 DB、FCV 讀 DB），彼此**沒有函式呼叫**。唯一共用的是 pymysql 連線樣板（可容忍重複）。因此技術上沒有「必須放同一 repo」的拉力，而分開能換得明顯的乾淨度。

**最終決定（2026-07-03，已執行）**：採「自有全新 repo」落地 → 已建立 **`stock_factor_collector`**（見 §📍 環境地圖與 Changelog）。以學長 TW collector 為種子（factory US 插槽 + Database 寫入層 + TW 範本），台美統一定位、保留 `CollectorFactory(country)` 分派。FMP API key 與 DB 帳密放 gitignored 的 config/`.env`（比照 `config.ini`）。

## 13. D8 分析：美股是否寫進同一個 `lab` DB

前提：`lab` 現況**已台美並存**（美股約 9451 家在庫），用 `exchange_name` 區分市場。

| | 同一 `lab`（台美並存） | 另開 DB（如 `lab_us`） |
|---|----------------------|------------------------|
| 讀取層改動 | 小（多一個 market 的 WHERE） | 大（依 market 切換連線、兩份 config） |
| 跨市場組合（Fund House） | ✓ 直接 union/join，未來輕鬆 | ✗ 跨 DB 查詢或程式端 merge，摩擦大 |
| 維度表共用 | ✓ company/factor 共用、schema 一致 | ✗ 重複維護 |
| 保護台股 | ~ 需靠紀律（market 圈定 + 回歸測試） | ✓ 物理隔離 |
| 與現況一致 | ✓ 延續台美並存 | ✗ 需遷移/重做 |

**建議：維持同一個 `lab`**，因論文終點是 Fund House 跨市場組合，單一 DB 讓那步輕鬆很多；符合接法 A 單一交會點。
**風險控制**：(1) 美股寫入/刪除一律帶 `exchange_name IN (美股)` 條件，只碰美股列；(2) 動完 DB / 讀取層後跑台股回歸測試；(3) `filing_date` 為可為空新增欄，對台股無害。
**重抓操作**：D2 選重抓 → 第一次「依 market 刪舊美股列 → 插入 FMP 新資料」，刪除務必帶美股條件，勿誤刪台股。
