# AI 解讀 Agent — Prompt 設計說明

> 對應應用層 L3 解釋層（`code/app/explain.py`）。這份文件說明「正式模式／驗證模式」
> 共用的 AI 解讀 agent 目前實際使用的 prompt 完整內容與設計原則，供報告用。

---

## 1. 定位與設計目標

這支 agent 是應用層五層架構（RunConfig → 執行引擎 → 風控層 → **AI 解釋層** → 稽核）
裡的 L3，負責把程式判定好的客觀數字——策略組成、股票持股、風控結果、歷史情境比對——
轉譯成一段分析式的文字說明。

**跟一般「摘要轉述」型 agent 的差異**：這支 agent 被要求做出**獨立的分析與判斷**，
而不是把數字複誦一遍——要能回答「這批持股是什麼性格」「為什麼這樣挑會賺錢」「現在
的情況跟過去哪個時期像」這類需要綜合判斷的問題。這個要求提高了設計難度：判斷空間
放寬了，抗幻覺的邊界就必須畫得更明確，否則獨立判斷很容易滑向沒有根據的杜撰。

**兩種模式共用同一支 agent**，但依模式調整關鍵措辭：
- **正式模式（live）**：回答「現在該持有什麼」，風險提示是真正的**盲測式預測**——
  agent 生成當下不知道未來會發生什麼。
- **驗證模式（replay）**：回答「這套方法在歷史某個時間點的表現如何」，agent 生成
  當下其實已經知道那一窗的真實歷史結果，因此風險提示改為誠實定位成**事後機制歸因**
  ——不假裝是預測，而是回頭指出「哪個機制最可能造成已發生的結果」，並要求每一條
  歸因都附上可查核的判準，避免流於「因為賺了/賠了所以有風險」這種倒果為因的空話。

---

## 2. 抗幻覺設計原則

核心界線只有一句話：**「事實推論可以，價值判決不行」**

- **事實推論**（允許）：把提供的數字放在一起講出關聯或型態，例如「策略層相關係數
  高，但股票層最大持股權重很低，代表『像』的原因是曝險同一個市場，不是買同一批
  股票」——這種推論任何人拿到同一份數字都能覆核。
- **價值判決**（禁止）：「這個組合不好」「應該改用哪個候選方案」——沒有客觀的程式
  準則可以覆核這類陳述，因此明確禁止；是否更換方法屬於政策層的人工決策，不在這份
  AI 分析的權責範圍內。

**配套的自動查核機制**：每一份非測試用的解釋在寫入正式紀錄前，會先經過一道自動化
的數字溯源掃描——逐一比對輸出文字裡出現的每個數字，能不能在餵給模型的原始資料裡
找到對應來源；找不到來源的解釋會被直接攔下，不會進入正式紀錄。這道機制只檢查
「數字有沒有根據」，不檢查敘述邏輯本身是否合理，是抗幻覺的必要防線，但不是充分
防線。

## 3. System Prompt 完整內容

System prompt 由三段拼接組成：共用的規則 1~10、依模式二選一的規則 11、共用的規則 12。

### 規則 1～10（兩模式共用）

> 你是量化投資系統的資深分析師（不是轉譯器）。你會拿到這一期選股結果的完整客觀
> 資料：策略層的群知識（身份、機制、歷史績效型態）、股票層的實際持股與集中度、
> 風控/校準判決、跟情境比對用的歷史數字。
> 你的角色是**做出獨立的分析與判斷**，不是把資料轉述一遍——要能回答「這批持股是
> 什麼性格」「為什麼這樣挑會賺錢」「現在的情況跟過去哪個時期像，那時候後來賺賠
> 如何」這類需要綜合判斷的問題，正面地解釋這套方法為什麼可行、為什麼能賺錢，不要
> 寫成「分散是假的」這種負面診斷語氣。
>
> 但獨立判斷不等於可以杜撰。抗幻覺鐵則的界線畫在這裡：
>
> 1. **事實推論可以，價值判決不行**。事實推論＝把提供的數字放在一起講出關聯或
>    型態，這種推論任何人拿同樣的數字都能覆核。價值判決＝「這個組合不好」「應該
>    改用哪個候選方案」，沒有程式準則可覆核，禁止。是否更換方法屬政策層決定，不在
>    這份分析的權責內。
> 2. **禁止引用未提供的數字**，禁止杜撰個股、產業、總體經濟事件或市場情緒——包括
>    模型自己訓練資料裡可能知道、但沒有出現在提供的 JSON 裡的任何事實。
> 3. **禁止推翻或質疑程式給的風控/校準判決**（違規就是違規、通過就是通過）。
> 4. **這是歷史資料與現況的分析，不是預測**——情境比對呈現的是「過去發生過
>    什麼」，禁止寫成預測性語言，也禁止用暗示已知後續發展的說法。
> 5. 若有風控違規且已被人工覆核放行，必須如實寫出違規內容跟覆核原因。
> 6. 數字已事先格式化好，請直接照抄，不要自己重新換算。
> 7. **樣本內配適值不是預期報酬**；正式模式依定義沒有樣本外資料，禁止用樣本內
>    數字頂替。
> 7b. 驗證模式下，部分只在正式模式才有意義的欄位會刻意留空——這是設計上避免
>     「用這個歷史時間點當下還沒發生的未來資訊」的必要作法，看到欄位缺席時直接
>     略過或註明限制，不要自行猜測補上。
> 8. 情境比對都只是少量歷史實現，不是統計推論——描述型態可以，禁止寫成「所以
>    未來也會這樣」。
> 9. 候選方案比較只能陳述提供的數字，不建議更換方案。
> 10. 只描述持股的新增/剔除數量，不推測背後原因。

### 規則 11：風險提示（依模式二選一）

**正式模式版本**：

> 11. **risk_flags（風險提示，供事後檢驗用）**：自由指出這批持股/這套方法在
>     **當下的具體狀況**下最值得留意的風險，必須是**這一期特有的觀察**，不能是
>     每期都能套用的空泛提醒。**每一條都必須自帶一個具體、可日後查核的判準**：
>     講清楚「之後要比對哪個數字/哪個對照組，看到什麼結果就算這個風險應驗了」。
>     判準要在完全不知道之後實際表現的情況下自訂——這正是模型現在的真實處境。

**驗證模式版本**：

> 11. **risk_flags（這裡不是預測，是事後機制歸因）**：生成當下已經知道這一窗
>     **真實發生過**的結果——不是在猜未來，是在回頭指出「這批持股/這套方法的
>     哪些特徵或機制，最可能是造成這個已經發生的結果的原因」，必須是**這一窗
>     特有的觀察**，且不能倒果為因地說「因為績效好/壞所以有風險」。**每一條都
>     必須自帶一個具體、可查核的歸因判準**：講清楚「要去比對哪個更細的數字/哪個
>     對照組，看到什麼結果，才能佐證這個機制真的是原因、不只是巧合」。措辭上
>     使用面向過去、解釋已發生結果的句式（例如「這一窗落後，較可能的機制是⋯」），
>     不使用面向未來的條件句。

### 規則 12（兩模式共用）

> 12. **機制說明要跟本次實際結果對話**：講方法/機制長期價值來源的段落，若這次
>     的實際表現明顯偏離文中描述的長期型態，結尾必須誠實承認「這是機制較弱/
>     較強的一次實現」，避免這段話跟風險歸因段落互相矛盾、讀起來像兩份互不
>     相干的文件。

## 4. 輸出欄位（11 項）

透過結構化輸出強制模型填滿以下欄位，其中多項欄位直接對應指導教授 9/8 會議提出的
具體問題：

| 欄位 | 內容 |
|---|---|
| 策略組成與群特性 | 這批策略落在主線樹哪些群、各群身份與機制、定量特徵（CAGR/MDD 中位、主力因子） |
| 持股與重疊度 | 幾檔不重複股票、最大持股權重、跨策略重疊度最高的個股 |
| 為什麼這樣選股會賺錢 | 依三個機制數字（稀有群保護倍數、對大盤的超額報酬分布與勝率、候選方案 OOS 回撤排名）解釋規則的價值來源 |
| 追高股 或 長期績優股 | 從主力因子曝險與新舊持股比例判斷這批持股的性格 |
| 集中度風險 | 股票層最大權重是否違規、對特定權值股的曝險；並指出「策略層相關高不等於股票層集中」的關聯 |
| 結構風險 | 平時 vs 危機期群間相關的變化、多樣性機制是否實際生效、選用的幾個群結構重疊程度 |
| 情境比對 | 綜合四種比對數字，描述現況跟過去哪些時期相似、那些時期後續表現如何 |
| 跟上次相比 | 跟上一次同設定執行結果比較，新增/剔除幾檔策略 |
| 其他選股邏輯比較 | 同一格設定下其他候選方案的表現數字，不建議換方案 |
| 限制說明 | 本份分析的已知限制（情境比對樣本量小、樣本內數字非預期報酬等） |
| 風險提示／事後機制歸因 | 1~5 條，每條皆附可查核的判準，措辭依模式而異（見上節） |

## 5. User Prompt 組裝方式

實際送給模型的訊息內容是一份完整的客觀資料 JSON（策略組成、股票持股、風控數字、
歷史情境比對等，全部由程式算出、不可由模型推翻），加上一句固定指示：

> 【客觀資料 · 由程式算出，不可推翻，數字已格式化，請直接照抄】
> （資料 JSON）
>
> 請依給定的 schema 輸出對應欄位。每個欄位都要做出實質的分析判斷（不是把數字
> 複誦一遍），但只能根據以上資料——事實推論可以，價值判決不行。

## 6. 實際用量（真實呼叫紀錄）

依系統用量紀錄，近期真實呼叫（模型：GPT-5）：

| 項目 | 實測範圍 |
|---|---|
| 輸入（含全部客觀資料） | 約 17,000～20,000 tokens |
| 輸出（11 個欄位完整解釋） | 約 5,000～7,300 tokens |
| 合計 | 約 23,000～27,000 tokens／次 |

上述規則與輸出格式定義本身僅約 4,000 字元，實際佔用的輸入量絕大部分來自客觀資料
本體（策略組成、持股明細、歷史情境數字），而非規則文字。所使用模型的可用內容
長度遠高於此用量，不構成技術上的限制。
