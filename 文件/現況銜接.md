## 5. 這次踩過的坑（重複踩會浪費很多時間）

1. **T8 不能拿來算群佔比**（2026-09-09 實跑抓到，差 2.8~3.6 倍）
   `ops.tools.t8_compute_portfolio_risk` 的 `cluster_coverage` 對到的是**凍結的全域六棵樹**（固定 k），
   但 walk-forward 每一窗自己重建的樹（`k_mode="silhouette_is"`）群數完全不同，兩者對不起來。
   → 群佔比要讀 `engine.Holdings.cluster_info`（該窗自己算好、已凍結的正確數字）。
   T8 只能用來算**跟分群無關**的 `portfolio_mdd`／`portfolio_ann_vol`。
   ⚠️ 這個教訓對未來的 `live` 模式同樣成立（T9 重建的新樹也不在 `cluster_assign.parquet` 裡）。

2. **anchored 不要改成 rolling**——H-26 已實測 rolling 是 13 個方案裡**最差**的
   （OOS CAGR 20.95% vs anchored 22.44%）。曾有外部審查建議改成「往前抓 72 個月」，那就是 rolling，已明確排除。

3. **測試 130/131 不一定是程式壞了**——唯一會掛的 `t_ops_t11_regime_label_valid` 需要即時資料庫，
   資料庫沒開就會失敗，其餘 130 項都吃凍結資料。

4. **文件路徑會過期**——2026-09-09 全面查證發現 CLAUDE.md 有 9 個指向不存在檔案的死連結
   （包括它自稱「最重要」的那份）。**改檔名/搬檔案後記得回頭更新引用**，
   也因此本次把 `老師9-8意見待報告事項_2026-09-15.md` 改名為 `_下次會議10-01.md`（日期式檔名容易誤導）。

5. 🔴 **HRP 只用來「分群」，從來沒有用來「配權重」**（2026-09-10 查證，差點寫錯設計）
   `walkforward_matrix.py:406` 的 `_portfolio_series` ＝ `wide.loc[members].mean(axis=0)`，
   `_evaluate()` docstring 也明寫「**等權**組合績效」——**8,370 格驗證的全部是等權組合**。
   `ops.tools.t9_compute_weights` 確實能算 HRP 權重，但**拿它當實際權重就跳出驗證空間了**，
   還會讓 C2 的 8% 上限失去依據（那是從 `1/n_members` 反推的）。
   ⚠️ 另外 `allocation="equal"/"proportional"` 決定的是**各群分到幾個代表名額**
   （`walkforward_matrix.py:539` 的 `allocate()`），**不是投組權重**，很容易望文生義搞錯。

6. 🔴 **候選池是「全期間贏過基準」篩出來的**（2026-09-10 實跑 `strategy_marks.parquet`）
   `passes_alpha_gate` TW 7,128/7,128、US 8,682/8,682 **皆 100%**。
   ⇒ walk-forward 的 **OOS 絕對數字系統性高估**（相對比較不受影響，共同座標軸成立）。
   **任何 OOS CAGR/MDD/Sharpe 的絕對值都不可當成「預期報酬」寫出去。**
   已補進 v10 §8 與 `應用層開發追蹤.md` §8-R1，建議 10/1 主動向老師報告。

7. **`k_stability.csv` 是查表不是現算**——`walkforward_matrix.py:427` 用
   `(tree_key, is_start, is_end)` 當 key，**任意 IS 區間查不到會直接 `raise KeyError`**。
   要支援使用者自選區間，必須現場跑 `silhouette_scan`（台股 7,128 檔 ⇒ 7,128² 距離矩陣
   × 約 9 個 k），成本尚未實測過，不要憑感覺假設「幾十秒就好」。

8. **`app/ui.py` 不能被 import**——它是 Streamlit 腳本，`from app.ui import X` 會把整支
   從頭執行一次（bare mode）然後炸掉。測試一律用
   `AppTest.from_file(<絕對路徑>)` ＋模擬互動，**且路徑要用絕對路徑**
   （相對路徑是相對於呼叫端腳本的位置，不是 cwd）。

9. 🔴 **`min_is_months` 不是那一列的 IS 長度，`n_is_months` 才是**（2026-09-10 踩到，
   而且**害我做出一個無效分析並寫進文件**，見 `應用層開發追蹤.md` §8-R9）
   `min_is_months` 是**第一窗**的 IS 長度；anchored 的 IS 會逐窗成長
   （方案 A：72→96→120→144→168→**192**；方案 E 第 4 窗到 **204**）。
   ⚠️ 更關鍵：**anchored 的 `is_start` 恆為錨點，所以給定 `oos_start`，IS 長度就被完全決定**
   ⇒ 「控制 OOS 期間後比較不同 IS 長度」這種分析在 anchored 資料上**做不出來**，
   每一列只會有一個 IS 長度。當時看到「四種 IS 長度算出完全相同的數字」還以為是
   有意義的發現，其實是**它們本來就是同一個窗**。
   **實測過的最長 IS ＝ 204 個月；台股共同窗全長 ＝ 228 個月**（`SCHEME_TOTAL_MONTHS`）。

10. 🔴 **要「全歷史的樹」之前先看 `_frozen/stage3/`——很可能已經有了**（2026-09-10）
    `contracts.HRP_WINDOWS` ＝ TW `("2007-01","2025-12")`／US `("2002-01","2025-12")`／
    XM `("2007-01","2025-12")`，主線六棵樹就是建在這些**完整共同窗**上
    （TW 228 月、US 288 月、XM 228 月），TW_normal **k=6、6,679 檔**。
    ⚠️ 分辨 `normal` vs `crisis`：**`normal` 才是連續完整窗**，`crisis` 是危機月份子集
    （TW 只有 17 個月），兩者策略宇宙相同、只換觀察窗。
    ⚠️ `contracts.py:57` 註解寫「TW 保留 7,160/7,162」是**候選池修復前的舊數字**，
    正確為 7,125/7,128，再經 `is_usable` 過濾為 **6,679**（程式不讀那行註解，不影響結果）。

11. **快時鐘的「今天」其實不是今天**——三層截斷：①台股財報套法定公告期限
   （`format_data.py:158`，Q2 要 8/31 才生效）②財報 frame 被 `price_index.max()` 截掉
   （`fcv_core.py:196`）③`resolve_holdings` 取 ≤ 指定日的最近交易日。
   2026-09-10 實測結果：UI 點「今天」實際落在 **2026-07-24 ＋ 2026Q1 財報**。
   這反而讓橫斷面很乾淨（不完整的 2026Q2 自動被排除），但要知道有這個落差。

## 6. 應用層速查（新加的部分，其他文件還沒完整涵蓋）

```bash
cd code                                   # 一定要在 code/ 底下跑（config.ini 是相對路徑）

# CLI
python -m app.cli new-config my_run.json --market TW --scheme A --window-no 6
python -m app.cli run my_run.json                    # 會寫稽核紀錄
python -m app.cli run my_run.json --no-record        # 只看數字，不留紀錄
python -m app.cli run my_run.json --memo             # 加 AI 備忘錄（dry-run，不花錢）
python -m app.cli run my_run.json --memo --live-llm --llm-purpose cluster_story

streamlit run app/ui.py
```

`memo.py`(L3) → `cli.py`／`ui.py`(L4)，`audit.py` 記錄每次執行。
決定事項與門檻依據全部在 `應用層開發追蹤.md`。
