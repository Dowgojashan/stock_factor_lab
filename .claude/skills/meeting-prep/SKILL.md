# 開會前：盤點 → 報告順序

## 步驟

### 1. 盤點「上次會議至今做了什麼」

不要憑印象列，用這些來源交叉確認：

```bash
git log --oneline --since="<上次會議日期>"           # 實際改了什麼
ls -lt _analysis_outputs_robustness/*.md | head      # 新產出的分析
```

再看追蹤文件的狀態欄（`開發待辦追蹤.md`／`應用層開發追蹤.md`）哪些從 ☐ 變成 ☑。

### 2. 逐項對照老師上次交代的事

打開上次會議整理出的待辦，**每一項都要有明確狀態**：完成／進行中／卡住／判斷後沒做。
「卡住」跟「判斷後沒做」一定要報告並說明理由——老師交代的事默默沒做是最糟的情況。

### 3. 挑報告內容：結果導向

🔴 **這是使用者的明確規則**：給老師的報告**不要放除錯過程、bug 修正史**。
老師關心的是「結論是什麼、方法站不站得住腳」，不是你怎麼把程式修好的。

| 要放 | 不要放 |
|---|---|
| 結論與數字（要有佐證） | bug 怎麼發現怎麼修的 |
| 方法論上的取捨與理由 | 開發過程的曲折 |
| 推翻了什麼既有說法 | 工具/環境問題 |
| 已知限制（誠實揭露） | 還沒驗證的猜測 |

（進度報告／bug 報告是**另一種文件**，兩者要分開，不要混在一起給老師看。）

### 4. 排順序

建議結構（參考 `文件/老師9-8意見待報告事項_下次會議10-01.md` §4 的作法）：

1. **上次交代的事的答案**——老師最想先聽這個
2. **推翻既有說法的發現**——愈早講愈好，因為會影響後面所有討論的前提
3. **需要老師拍板的決策**——留足夠時間討論
4. 其他進度

### 5. 準備追問備援

針對每個要報的結論，先想「老師會問什麼」，把佐證資料/圖表位置先找好。
這個專案已有前例：`_analysis_outputs_robustness/穩健性檢定_回應老師的四個質疑.md`
就是被問了之後才補的——能先準備就不要等被問。

若時間允許，對主要結論跑一次 `methodology-review` skill，先自己找出弱點。

### 6. 🔴 明確標出「需要老師拍板」的項目

**這是最容易在會議中漏掉的**——講完進度時間就沒了，該問的沒問，又要等下一次。
把決策點獨立列成一張清單，開會時照著問。

目前累積的待拍板事項見 `文件/研究框架總覽_v10.md` §10.3 與 `文件/現況銜接.md` §3。

### 7. 產出

在對話框給出報告大綱與建議順序即可。**需要文件時使用者會明講**——
不要主動生成一份報告文件。
