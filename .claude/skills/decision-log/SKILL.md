# 決策留痕

## 為什麼

這個專案的決定都不是憑感覺定的，而且**事後一定會有人問「為什麼是這個數字」**
（老師會問、口委會問、三個月後的自己也會問）。已有的好例子：

- **C2 單一股票上限 8%**：不是隨便訂的，是從 900 格歷史資料反推——legacy 比例的單檔權重
  歷史最大值 4.00%，取 2 倍留緩衝 → 8%
- **openSec 變體**：primary 嚴格、secondary 全開，理由是「Phase 1 檢定的是因子自己能不能
  單調預測，但 secondary 的功能是提供不同構面資訊，兩件事不一樣」，台美股都獨立驗證過
- **anchored 不用 rolling**：H-26 實測 rolling 是 13 個方案裡最差的（20.95% vs 22.44%）

反例（要避免的）：只寫「決定用 X」而沒寫為什麼，半年後沒人知道能不能改。

## 一筆決策紀錄要有的欄位

| 欄位 | 說明 |
|---|---|
| **決定** | 一句話講清楚定了什麼 |
| **依據** | 🔴 **要有數字，而且要能指到來源檔案**。「從實測資料反推，不是猜的」是這個專案的標準 |
| **排除了什麼** | 考慮過但沒選的替代方案 |
| **為什麼排除** | 每個替代方案各自的排除理由（有數字最好）|
| **誰決定的** | **老師裁示** vs **自己判斷**——這兩者的可更動性完全不同 |
| **何時要重新檢視** | 什麼條件成立時這個決定要重新考慮（例如「擴到 XM 市場時 C3 門檻要重訂」）|

## 步驟

### 1. 先確認依據是真的查證過的

如果決定的依據是「我覺得」「一般來說」「通常」，**先去查**——
跑一次資料、查一次程式碼，把它變成有數字的依據。查不出來就誠實寫「暫定，尚無資料支撐」，
並列入「何時要重新檢視」。

### 2. 記錄替代方案

**沒被選上的方案也要寫**。這是最常被略過、但事後最有價值的部分——
之後有人（包括你自己）想提「不如改用 X」時，可以直接看到 X 當初為什麼被排除，
不用重跑一次討論。

⚠️ 這個專案發生過：外部審查建議改用 rolling 窗，若當初沒記錄「H-26 已實測 rolling 最差」，
就會白白改成一個已知較差的設計。

### 3. 標註決定的來源層級

- **老師裁示**：要保留原話引用，不可自行推翻，要改也要再問老師
- **自己判斷**：可以改，但要有新證據
- **暫定**：還沒有足夠資料，先這樣跑，之後要回頭確認

### 4. 寫進對應文件

| 決定類型 | 寫到哪 |
|---|---|
| 應用層設計 | `文件/應用層開發追蹤.md` §3 決定事項表 |
| 研究部實驗設計 | `文件/開發待辦追蹤.md` 對應項目 |
| 影響整體框架/論文 | `文件/研究框架總覽_v10.md` |
| 「已決定不做」的事 | 🔴 也要加進 `文件/現況銜接.md` §4，避免新對話框重新提案 |

### 5. 標日期

每筆都要有日期。這個專案的文件慣例是 `⚠️ 2026-09-09 review 補充：...`
這種行內標註，方便之後判斷哪個說法比較新。
