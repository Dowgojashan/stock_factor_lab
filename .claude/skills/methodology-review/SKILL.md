# 方法論審視

## 核心原則

🔴 **不接受憑印象回答。** 每一項檢查都要實際去查程式碼、重算數字或跑指令驗證。
使用者的第一鐵則就是這個——講「應該沒問題」而沒有查證，比沒檢查更糟，因為會給人錯誤的安心感。

🔴 **這個專案的歷史證明：最危險的錯誤都不會報錯。** 例如美股動態條件 C 曾整組失效
（「較上季升」恆假），程式跑得很順、數字很漂亮，只是全錯。所以檢查重點不是
「程式會不會壞」，而是「如果這裡錯了，我看得出來嗎」。

## 步驟

### 1. 先讀陷阱清單

讀 `pitfalls.md`（與本檔同目錄）。裡面八類陷阱**每一條都是這個專案真的踩過或檢定過的**：
前視偏誤、倖存者偏誤、資料窺探、共同座標軸、IS/OOS 分離、資料層靜默錯誤、
結論過度延伸、可重現性。

### 2. 界定審視對象

先確認要審的是什麼，不同對象檢查重點不同：

| 對象 | 重點 |
|---|---|
| **實驗設計**（還沒跑）| 共同座標軸、對照組、前視偏誤、能不能證偽 |
| **已有結論**（跑完了）| 有沒有更無聊的解釋、數字能否溯源、是否過度延伸 |
| **系統/程式設計** | 靜默錯誤、可重現性、凍結鏈 |
| **要報給老師/寫進論文的內容** | 全部都要，外加「會被怎麼挑戰」 |

### 3. 逐項檢查，每項都要有證據

對 `pitfalls.md` 的八類逐一過。**每個結論都要附證據**：

- 「檢查過沒有前視偏誤」→ 要能說出：這個參數是用哪段資料決定的、在哪一行程式
- 「數字正確」→ 要能指出來源檔案，或當場重算一次
- 「對照組公平」→ 要能列出兩組之間所有不同的地方，確認只有一個維度在變

查證常用位置見 `meeting-followup` skill 的「數字有沒有過期」對照表。

### 4. 特別針對「好結果」做證偽

只要出現漂亮的結果，**先假設它是假的**，然後找證據推翻這個假設：

- 有沒有更無聊的解釋？（市場 beta？規模效應？運氣？資料錯誤？）
- 換一組參數/期間/市場還成立嗎？
- 有沒有辦法設計一個「如果結論是真的，這個檢定就該通過」的檢定？

**M 系列就是這樣做出來的**——原本以為 HRP 分群有貢獻，做了對照後發現相關結構
幾乎全由市場 beta 決定、分群在報酬上沒有貢獻。推翻自己的結論不是失敗，是研究品質。

### 5. 分級輸出

| 等級 | 定義 |
|---|---|
| 🔴 **會讓結論不成立** | 必須修，修不了就要改結論或撤回 |
| 🟡 **會被挑戰但可辯護** | 準備好說法，或誠實標成已知限制 |
| 🟢 **已知限制，已揭露** | 確認文件裡真的有揭露就好 |

對每一項寫清楚：**問題是什麼、證據在哪、會怎麼影響結論、建議怎麼處理**。

### 6. 誠實回報

如果檢查完發現**沒問題**，就說沒問題，不要為了顯得認真而硬湊問題。
但要說明「查了哪些、怎麼查的」，讓使用者能判斷這個結論的可信度。

反之，如果發現的問題會推翻已經報告給老師的內容，**要明講**，
並建議是否需要在下次會議主動更正——這個專案有這個慣例（M 系列推翻故事線就是主動報告）。
